# Dearby 네이티브 명세 — Seed 확정

2026-09-27. 이번 대화의 직접 승인 사항과 미정 사항을 분리한다. 완료된 구현 명세나 출시 승인을 뜻하지 않는다. 사용자 선택: 제품 방향을 다시 기획하지 않고 현재 기획을 개발 가능한 명세로 확정한다. 과거 웹/추천 중심 Seed를 이번 네이티브 범위의 정본으로 간주하지 않는다.

## 확정한 경험

- iOS·Android 네이티브 앱, 최신 스택 검토. 웹 실행 구현 제거 승인. 이전 플랫폼별 Orca 하위 worktree·세션, 기능별 커밋, GitHub 이슈/PR 및 문서 인계 방식 유지.
- 흰색·청록색 디자인. 하단 탭은 발견 / 저장 / QR / 받은 명함 / 내 프로필.
- 발견은 모집 중 활동 목록이며 검색창과 내 명함 영역을 두지 않는다. 활동 상세는 기본 정보·소개·일정·참가 안내·장소·출처를 제공한다.
- 연결한 기기 캘린더와 일정 충돌을 비교한다. 모달 타임라인에서 겹치는 시간을 하나씩 확인하고 마지막 확인 후 닫는다. 권한 없음과 충돌 없음은 구분한다.
- 외부 신청 웹뷰를 닫으면 신청 여부를 직접 입력받는다. 신청 표시는 실제 참가 확정과 다르다. 신청한 상세는 헤더 아래 체크 아이콘과 얇은 고정 안내 바, 공식 사이트 보기 버튼을 제공한다. 신청 상태 수정 가능.
- 외부 폼 자동 입력과 부족 정보의 앱 저장을 구현한다. 사용자 선택(2026-09-27): 지원 사이트를 정해 검증하고 나머지는 웹뷰에서 직접 입력한다. 인증·동의·최종 제출을 사용자가 수행한다. 첫 지원 대상은 사용자가 지정한 if(kakao) 참가 신청이다. 2026-09-27 공식 if(kakao)26 페이지의 참가신청 버튼에서 카카오 계정 로그인 요구를 실제 브라우저로 확인했다. 로그인 이후 필드·자동입력·iOS/Android 웹뷰 호환성은 아직 미검증이다. 지원 완료로 표시하지 않으며 폼별 검증 후 지원 범위를 명시한다. 모든 사이트 동작을 보장하지 않는다.
- 내 프로필은 전체 프로필 상세를 바로 표시한다. 편집, 연락처 추가, 활동 이력 추가를 제공하고 하단 생성 CTA는 없다. 전화·이메일·카카오톡·인스타그램·GitHub·Behance를 입력한다.
- 전체 프로필 1:N 활동 이력, 전체 프로필 1:N 공유 프로필. QR 또는 공유 링크 생성 시 공유 프로필이 생긴다. 공유할 연락처와 이력을 선택할 수 있다. 전체 선택/부분 선택을 지원한다. 연락처 숨김은 사선·색과 토스트로 표시한다.
- UI에서는 공유용 구성의 명칭을 명함으로 사용한다. 생성·게시에는 로그인 필요. 받기·기기 저장에는 로그인 불필요.
- 로그인은 이메일 인증 방식으로 확정(2026-09-27 사용자 3번). Apple·Google·카카오 소셜 로그인은 이번 선택에 포함하지 않는다. 인증 UX는 이메일로 받은 인증번호를 앱에 입력하는 방식으로 확정(후속 사용자 1번). 이메일 로그인 링크나 비밀번호 방식이 아니다. 만료·재전송·시도 제한·계정 복구 정책은 구현 시 구체화하며 만료/오입력/재전송/네트워크 실패를 검증한다.
- 비로그인 저장은 이미지가 아닌 공유 명함 ID를 저장한다. 나중에 로그인 시 계정에 등록할 수 있어야 한다. 앱 삭제 시 복구할 수 없다는 안내를 제공한다.
- 로그인 후 “기기에 저장한 명함 가져오기” 선택 화면을 제공한다(2026-09-27 사용자 수정 제안 및 “좋아요” 승인). 이전 일괄 확인 방식은 이 선택 화면으로 대체한다. 이름·직무·교환한 활동·체크박스를 표시하고 전체 선택/선택 해제, “선택한 명함 N개 가져오기”, “나중에”를 제공한다. 대상은 Dearby에 기기 저장한 명함이며 휴대폰 주소록 가져오기가 아니다. 선택하지 않은 명함과 가져오기에 실패한 명함은 기기에 보존한다. 동일 공유 명함 ID 중복 방지, 초기 선택 상태, 재진입 위치, 성공 후 로컬 데이터 처리의 세부 계약은 구현 시 구체화한다.
- QR 탭은 보여주기/찍기. 보여주기는 큰 QR·작은 명함 이름과 회색 설명, 우상단 공유 메뉴, 명함 보기, 하단 명함 선택 목록을 제공한다. 공유 메뉴에서 링크 공유·복사·QR 이미지 저장.
- QR을 누르면 다른 요소 없이 QR만 표시하며 다시 누르면 복귀. 기본 화면에 정보 아이콘과 회색 안내. 새 명함 항목 선택 시 생성 안내 카드와 CTA를 표시한다.
- 받은 명함은 검색 가능. 내 명함을 주지 않은 상대/서로 주고받은 상대 영역을 좌우로 전환한다. 전자가 없으면 영역 구분 문구와 탭 없이 카드 묶음을 표시한다.
- 카드 묶음은 위아래로 넘기는 제안이 시안에 반영됨. 가로 영역 전환과 충돌하지 않도록 한다. 실제 제스처 검증 필요.
- 받은 명함과 내 명함 선택 카드의 상단은 항상 이름·직무. 접힘/펼침에서 위치를 유지한다. 아래 명함 제목·소개·연락처·활동 이력을 같은 순서로 표시한다. 내 명함은 작은 명함 이름표로 구분한다.
- 받은 명함에서 상세보기 제공. 나도 명함 주기는 QR 대신 내 명함 카드 묶음을 보여주고 명시적으로 이 명함 보내기를 선택한다. 우상단 + 새 명함 제공, 생성 후 선택 화면으로 돌아와 새 명함을 선택하되 자동 전송하지 않는다.
- 전달 방식 확정(2026-09-27 사용자 1번): 선택한 명함을 상대의 받은 명함함에 바로 추가하며 서버가 전달 성공을 확인하면 서로 주고받음으로 전환한다. 수락 요청은 없고 교환 완료는 열람 완료를 뜻하지 않는다. 실패·오프라인·응답 불명확 상태를 성공으로 표시하지 않는다.
- 교환 맥락 확정(2026-09-27 사용자 1번): 어느 활동에서 교환했는지 남긴다. Dearby 등록 활동 선택, 직접 입력, 선택 안 함을 모두 지원하고 활동 선택을 강제하지 않는다. QR 보여주기·내 명함 보내기의 교환 맥락으로 선택하며 받은 명함 요약·상세 이력·활동명 검색에 사용한다.
- 같은 사람과 반복 교환하는 경우 활동·날짜 이력을 명함과 별도로 누적하는 안을 제안했다. 중복 명함 처리의 정확한 단위(사람/공유 명함 ID)와 날짜의 의미는 구현 계약에서 확정해야 한다. 등록 활동 ID와 직접 입력 텍스트를 구분하며, 활동 선택만으로 실제 참가나 주최 측 검증을 증명하지 않는다.
- 신규 활동 알림은 새로 등록되거나 모집을 시작한 컨퍼런스·대외활동을 대상으로 한다(2026-09-27 사용자 1번 선택). 저장한 명함 소유자의 활동 이력 변경은 대상에서 제외한다. 수신 범위는 관심 조건에 맞는 신규 활동과 저장한 조직·프로그램의 새 모집 소식 두 종류이며 각각 켜고 끌 수 있다(사용자가 직전 1번 선택을 3번으로 정정). 구체 관심 조건·알림 빈도·동일 모집의 중복 알림 처리는 미정.

## 구현 계약에서 구체화할 사항

1. 확정(2026-09-27): 사용자가 3번 “논의한 전체 서비스”를 선택했다. 로그인·서버 기반 명함 교환·활동 수집·알림·기기 캘린더·외부 폼 자동입력을 첫 완료 범위에 포함한다. 기능별 구현은 허용하되 로컬 데모나 명함 교환만으로 전체 완료를 선언하지 않는다. 외부 자동입력의 지원 사이트 범위와 실제 운영 완료 기준은 후속 확인한다.
2. 이메일 인증 로그인은 확정. 이메일 인증번호 입력 UX까지 확정. 서버 운영 범위·비로그인 ID 귀속과 계정 통합·중복 처리는 미정.
3. 전달 방식 확정: 상대의 받은 명함함에 직접 추가, 서버 전달 성공 기준으로 교환 완료. 비로그인 수신자의 계정 연결·중복 요청·실패 재시도 정책은 후속 구체화한다.
4. 명함 구성과 발행본의 관계, 원본 변경·삭제·공개 철회와 이미 받은 명함의 처리.
5. 지원할 외부 폼 사이트와 자동입력 허용 정보, 캘린더 권한·선택·반복 일정 처리.
6. 최초 콘텐츠·신규 활동 알림의 출처·갱신·관심 조건·빈도. 전체 서비스 범위 포함은 확정.
7. 교환 맥락과 공유 명함의 분리: QR/링크 재사용 시 맥락 유지, 반복 교환 중복 기준, 작성자·수신자 수정 권한과 교환 시각의 의미.

## 검증 루프 초안

각 확정 요구에 ID를 부여하고 요구사항 → 플랫폼 코드 → 자동 테스트 → 실기/시뮬레이터 증거 → 이슈/PR을 연결한다. 미구현·데모 검증·OS 검증·실서버 검증을 분리한다. 구현 담당의 자기 검사 뒤 조율 세션에서 교차 검토하고, 실패 항목은 동일 담당에게 돌려보낸다. 과도한 설계 검토는 ponytail-review를 사용하되 정확성/접근성 검증을 대체하지 않는다. 이미지 생성의 임의 아이콘·간격 차이는 승인 요구로 취급하지 않는다.

## 외부 신청 조사 — if(kakao)

- 사용자 지정: kakao if → if(kakao) 참가 신청을 첫 지원 대상으로 해석.
- 공식 출처: https://if.kakao.com/2026 (2026-09-27 KST 확인). 공식 FAQ는 신청과 최종 참가자 선정을 구분한다.
- 실제 브라우저 관찰: 메뉴 열기 → 참가신청 → “카카오 계정으로 로그인해주세요.” 대화상자. 로그인을 실행하거나 개인정보를 입력하거나 신청을 제출하지 않았다.
- Dearby 자체 이메일 인증번호 로그인과 외부 if(kakao)의 카카오 계정 인증은 별개다. 외부 인증 세션을 자동으로 공유하거나 대체한다고 가정하지 않는다.
- 향후 검증: 사용자 외부 인증 후 실제 폼·필드 확인, 두 플랫폼 웹뷰 로그인/복귀, 사용자가 선택한 정보만 채우기, 부족 정보 입력·별도 저장 동의, 취소·실패, 최종 제출 수동 수행. 로그인 이후 폼 접근 없이는 실제 자동입력 지원 완료를 선언하지 않는다.

구현상 가역적 세부(간격·오류 문구·내부 버전 고정 등)는 담당자가 근거를 기록해 결정한다. 사용자 결과를 바꾸는 개인정보 공개·반복 교환 식별·공유본 갱신/철회 정책은 자동 확정하지 않는다. 실서버·실기기 검증을 fixture/시뮬레이터 통과로 대체하지 않는다. 앱스토어 게시 여부는 별도 배포 범위로 남아 있다.

## 차단 사항 처리 — 사용자 직접 지시

개발 중 막히면 사용자 질문으로 멈추지 않고 GitHub 이슈에 원인·영향·증거·해소 조건·의존 작업을 남긴다. 의존하지 않는 다른 작업부터 계속한다. 개인정보 공개나 외부 권한을 확대하는 미정 정책은 임의 승인하지 않고 해당 경로만 보류한다. 가역적 구현 선택은 판단 근거를 기록한다. 이슈 등록은 해결이나 완료를 의미하지 않는다.
