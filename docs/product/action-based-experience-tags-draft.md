# 행위 기반 경험 구조 — 검토 초안

2026-09-22. 사용자 제안은 ‘현직자교류’를 ‘네트워킹 / 누구와: 현직자’처럼 분해하는 것이다. 직무탐색을 체험하기와 현업 등으로 표현하는 예시를 들었으며 더 적합한 행위 이름을 요청했다. 후속 사용자 확인으로 상위 활동 범주에 세부 경험이 포함되는 의미를 승인받았다. 네트워킹을 선택하면 현직자·동료 네트워킹을 포함한다. 후속으로 제작의 대상/방식과 행위별 선택 속성 구조도 승인됐다. 후속으로 사용자는 탐색·실무체험이 광범위하다며 과제수행·청강처럼 구체 행위로 분류하도록 요청했다. 아래 탐색·실무체험 표는 이전 제안이며 최신 방향은 마지막 절을 따른다. 최종 속성 사전·문구와 구현 구조는 미정이다.

## 승인된 포함 관계

- 네트워킹(교류)은 상위 범주다.
- 현직자와 네트워킹, 동료와 네트워킹은 그 안에 포함된다.
- 상위 네트워킹을 선택하면 해당 하위 경험을 제공하는 프로그램들도 검색된다.

검색 의미의 적용: 특정 하위 경험을 선택하면 그 조건으로 좁힌다. 하위가 확인되면 상위도 일치하지만 상위만 확인됐다고 특정 상대를 추정하지 않는다. 같은 프로그램은 부모/자식 일치 때문에 중복 집계하지 않는다. 실제 저장 구조를 반드시 트리로 구현하라는 의미는 아니다.

네트워킹의 상위/세부 포함 및 카드/필터 분리, 제작의 대상/방식 속성 구조는 승인됐다. 팀협업은 독립 상위 행위에서 수행 방식으로 정리했다. 탐색·발표의 최종 필드와 실무체험 추가는 모델 제안이다. 단일 행위에서 필요한 질문을 달리하여 모든 태그에 누구와/무엇을/어떻게를 일괄 강제하지 않는다.

### 유지할 경험 의미

- 네트워킹은 관계를 만들고 교류할 기회, 협업은 역할을 나누어 공동 과제를 수행할 기회로 구분한다. 협업만으로 별도 네트워킹 행사가 있다고 추정하지 않는다.
- 제작의 대상(웹 서비스 등)만으로 기존 프로젝트완성 경험을 대체하지 않는다. ‘어디까지 하는가’라는 수행 범위(시제품 제작, 결과물 완성, 출시 등)를 추가로 표현하는 안을 제안한다. 카드에는 원문 근거로 확인된 의미 있는 범위만 요약하고 실제 성공을 보장하지 않는다.
- 탐색은 직무/업무를 알아보는 활동, 실무체험은 실제 또는 유사 업무 과제를 직접 수행하는 활동으로 구분한다. 짧은 견학·설명 청취를 실무 수행으로 표시하지 않는다.
- 발표는 참여자 본인이 발표하는 경험이며 발표 관람과 구별한다.
- 프로필의 방향=백엔드와 협업의 상대=백엔드 개발자는 같은 이름이 나와도 역할이 다르다. 방향/경험의 의미를 섞지 않는다.

## 직무탐색과 실무체험

직무 설명을 듣고 업무를 알아보는 경험은 ‘탐색’, 실제 업무나 유사 업무 과제를 직접 수행하는 경험은 ‘실무체험’으로 구분하는 안이다. 현직자 강연이나 만남만으로 실무체험을 부여하지 않는다. 이번 모델 제안은 탐색과 실무체험을 별도 상위 유형으로 두는 것이다. 사용자 확인 전이며 기존 직무탐색의 이름만 실무체험으로 바꾸지 않는다.

## 방향과 경험

기존 방향 태그는 사용자가 나아갈 지향점이고, 구조화된 경험은 프로그램에서 하는 활동이다. 예: 방향=백엔드 / 경험=교류(현직자), 제작(웹 서비스). 방향/경험 두 축 구분은 승인된 기준이며 구체 어휘와 필드는 미정이다.

## 필터·순위 검토 사항

- 행위와 선택한 속성 묶음을 하나의 경험 조건으로 취급한다(2026-09-22 승인).
- 상위 교류와 그 하위 현직자 교류를 독립 경험 두 개로 세면 중복 점수가 생길 수 있다.
- 최우선 경험은 상위 행위만 또는 세부 조건을 붙인 묶음으로 지정할 수 있다(2026-09-22 승인).
- 조건 근거는 실제 회차/활동 내용에 연결하고 불확실한 세부 속성은 관리자 검토 대상으로 두는 안을 검토한다.
- 기존 다중 경험 OR·최우선 경험 우선·모집 상태 정렬 계약을 임의로 변경하지 않는다. 새 표현에 어떻게 대응할지는 후속 합의가 필요하다.

기획 검토 문서만 작성했으며 공통 계약·앱 코드·수집 데이터는 변경하지 않았다.

## UI 묶음 표현과 필터 분리 — 승인

사용자는 ‘네트워킹 | 현직자, 동료’처럼 상위 활동과 세부 값을 한 묶음으로 보여주는 안을 제시했고, 카드 표시와 검색 필터의 조작을 분리하는 제안을 “좋아요”로 승인했다. 카드의 왼쪽은 활동 유형, 오른쪽은 확인된 상대다. 같은 상위 활동명을 반복하지 않는다. 값이 많으면 일부와 ‘외 N개’로 요약하고 상세에서 전체를 보여준다.

네트워킹 자체의 근거는 있지만 상대가 불명확하면 상위만 표시하고 상대 후보는 내부 검토하는 안을 제안한다. 구분 기호의 디자인·칩 또는 텍스트 여부·클릭 범위·접근성 읽기 문구는 미정이다. 카드의 제공 경험 나열과 검색 필터의 선택 조건은 별개이며, 상위 선택으로 하위를 포함하는 의미는 유지한다.

필터는 ‘네트워킹 전체’와 개별 상대를 구분해 선택할 수 있게 한다. 상위 전체 선택은 모든 하위 경험을 포함하며, 여러 상대 선택은 하나라도 일치하면 포함한다. 정확한 컨트롤·요약 임계치·전체와 개별 간 선택 전환·접근성 표현은 미정이다. 부모와 자식의 중복 가산을 막는 내부 표현은 후속 명세 대상이다.

## 제작의 대상·방식 분리 — 승인

2026-09-22 사용자는 ‘제작: 무엇을=프로젝트, 어떻게=팀협업’ 구조의 장단점을 물었다. 후속 “좋아요”로 다음 보완안을 승인했다. 이전 6유형 초안의 팀협업은 독립 상위 행위로 고정하지 않고 수행 방식으로 정리한다.

- 행위에 대상·방식 등의 속성을 붙이면 사용자가 원하는 조합을 표현하기 좋다.
- 프로젝트는 과정/진행 단위라 결과물 종류를 설명하기에 넓다. 무엇을에는 웹 서비스·앱·디자인 결과물 등의 구체 대상을 제안한다. 원문에 없는 대상을 추측하지 않으며 불명확하면 상세 값은 보류한다.
- 어떻게에는 개인 수행/팀협업 등 방식을 둔다. 모든 유형에 동일한 속성 필드를 강제하지 않는다.
- 팀협업을 독립 태그와 제작의 속성 양쪽에서 가산해 동일 경험을 중복 점수화하지 않는다.
- 예: 활동=제작, 대상=앱 서비스, 방식=팀협업. 완성/출시까지 하는지는 추가 근거로 구분한다.
- 같은 프로그램에 개인 제작 활동과 별도 팀 토론이 있다고 제작+팀협업으로 합쳐서는 안 된다. 같은 활동 단위에서 결합된 근거가 필요하다.
- 다속성은 한 갈래 분류 트리와 다르다. 상위 선택이 세부 조건을 포함하는 사용자 의미와 물리적인 데이터 구조 결정을 구별한다.

초기에는 타입별 필수/선택 속성·어휘 목록·중복 계산 정책을 정해야 하며 실제 코드/공통 계약은 변경하지 않았다.

## 프로필의 경험 묶음 — 승인

2026-09-22 사용자 “좋아요”로 승인했다. 프로필에서 행위를 먼저 고르고 원하는 세부 속성을 선택적으로 추가한다. 예: 제작 → 대상=앱 → 방식=팀협업. 세부 조건은 건너뛰고 상위 행위만 선택할 수도 있다. 선택한 묶음 전체를 경험 1개로 다루며, 가장 원하는 경험은 ‘제작’ 전체 또는 ‘팀협업으로 앱 제작’ 같은 구체 묶음으로 지정할 수 있다.

속성별 복수 선택 규칙, 구체 입력 컨트롤, 부분 일치 후보끼리의 추천 순위와 검색 조건 완화 방식은 아직 미정이다. 전체 일치와 부분 일치의 차이를 숨기거나 일부 속성 일치를 최우선 경험 전체 일치로 간주하지 않는다.

## 복합 경험의 부분 일치 추천 — 승인

2026-09-22 사용자 “좋아요”로 승인했다. 가장 원하는 경험이 ‘제작 | 앱 · 팀협업’이라면 앱을 팀으로 제작하는 활동은 전체 일치, 앱을 혼자 제작하거나 웹 서비스를 팀으로 제작하는 활동은 부분 일치다. 부분 일치 프로그램도 추천에 포함하되 같은 모집 상태에서는 전체 일치를 먼저 노출하고, 부분 일치는 아래에서 실제 맞는 속성만 강조한다. 부분 일치를 최우선 경험 전체 충족으로 계산하지 않는다.

모집 상태 우선이라는 기존 계약은 유지한다. 부분 일치 간 대상/방식의 우선순위, 다른 희망 경험과의 교차 순위, 구체 점수는 미정이다. 이번 승인은 추천에 관한 것이며 검색 조건을 자동 완화하는 승인이 아니다.

## 구체 행위와 하위 태그 검색 — 최신 사용자 방향

2026-09-22 사용자는 탐색·실무체험을 너무 광범위하다고 판단하고 다음 예시를 제시했다. 이전 두 유형의 분리 제안은 채택하지 않는다.

- 과제수행 / 무엇을: 개발 과제, 서비스 기획
- 청강 / 무엇을: 업무 소개, 직무 설명회

사용자는 태그 검색 시 하위 태그도 찾을 수 있고, 하위 선택 시 상위도 함께 선택되는 흐름을 제안하며 복잡도를 질문했다. 후속 “좋아요”로 아래 복합 조건 선택과 상위의 세부 선택 상태 표시를 승인했다.

승인된 검색·선택 의미: 검색 결과에 ‘과제수행 | 서비스 기획’처럼 행위와 세부 값의 경로를 표시하고, 선택 시 하나의 복합 조건으로 추가한다. 부모는 해당 묶음의 소속과 ‘세부 항목 선택됨’ 상태를 표시하며 ‘과제수행 전체’를 독립 OR 조건으로 추가하지 않는다. 그렇지 않으면 서비스 기획만 골라도 다른 모든 과제가 결과에 포함된다. 같은 세부 명칭이 여러 행위에 쓰이면 행위별 후보를 구분한다. 모든 행위의 같은 이름을 자동 선택하지 않는다.

용어 정리: 직전 설명에서 내용을 중심으로 청강을 표현하고 형식은 필요할 때 추가하는 안도 제시했다. 이번 확인의 핵심은 복합 조건 선택 의미이며, 별도 형식 속성의 도입과 전체 어휘 사전까지 확정한 것으로 확대하지 않는다. 과제수행과 제작이 함께 있는 경우 동일 활동의 중복 가산 기준도 후속 검토 대상이다.

## 제작과 과제수행의 의미 경계 — 승인
