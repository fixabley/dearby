## 웹 전환 이후 최신 결정 — 2026-09-24

추가 확인: 컨퍼런스도 탐색할 활동에 포함한다. 선발형 활동과 참가등록형 행사를 함께 다루며 공고별 참가 대상·등록 마감·개최일·장소를 구분해 안내한다. shadcn/ui 사용은 선택지로 허용됐으며 필수 UI 교체 요청은 아니다.

사용자는 기존 실행 코드를 제거하고 웹으로 재구현하도록 요청했고, 첫 범위를 프로그램 탐색·필터·상세·조직/프로그램 스크랩으로 선택했다. 인터페이스는 YouTube와 같은 가독성 있는 구조로 대외활동을 보여주는 것이 목적이다. 이용자는 대학생으로 한정하지 않으며 고등학생·대학생·취준생 등도 포함한다. 아래 대학생 중심 정의와 미착수 기록은 당시 기획 이력이며 이 최신 결정이 우선한다. 공고별 참여 대상·조건을 표시하며 자격 미충족만으로 탐색에서 제외하지 않는 원칙은 유지한다.

이번 구현은 명시적인 가상 샘플과 브라우저 저장 기반 웹 프로토타입이다. 실제 모집 데이터 수집·API·계정·추천 학습·프로필 및 자격 자동 판정은 구현 완료로 간주하지 않는다. 실제 구현·검증 상태는 [웹 인계](../context/web-implementation-and-handoff.md)와 [조율 문서](../context/coordinator-current-task-and-decisions.md)를 따른다.

## 확정한 제품 정의

Dearby는 IT·개발에 관심 있는 대학생이 흩어진 교외 활동을 한곳에서 모아 보고, 원하는 직무와 경험에 맞는 활동을 빠르게 찾도록 돕는 앱이다. 사용자가 통합 정의에 “맞아요”로 확인했다. 지원 조건 비교·조직/프로그램 스크랩·결과 없음의 부분 조합 제안은 아래 세부 계약을 따른다.

목표: IT·개발에 관심 있는 대학생이 원하는 직무와 경험에 맞는 교외 활동을 빠르게 찾도록 Dearby 첫 버전의 검증 가능한 기획 명세를 완성한다.

- 필요 시 정보 입력·재사용·수정과 지원 조건 표시 및 조직·프로그램 스크랩 흐름을 정한다.

상태: Seed 합의 완료, 세부 기획 명세 작성 중이다. 프로그램별 탐색과 고유 프로그램 수 집계는 승인됐다. 최초 출처·갱신·중복 정책, 추천 보정과 성공 평가의 세부 명세는 미완료다.

## 사용자 목적과 초기 범위

가장 우선할 문제는 여러 사이트를 뒤지며 활동을 찾는 시간과 수고다. 몰랐던 적합한 기회 발견, 얻을 경험의 이해와 참여 판단도 함께 중요하다. 사용자는 지인·인스타그램 광고·구글 광고·구글 검색과 가끔 링커리어로 활동을 접했다. 공고사이트에 홍보하지 않는 연합동아리·부트캠프 등의 사례도 관찰했다.

| 구분 | 초기 방향 | 전체 범위 |
| --- | --- | --- |
| 이용자 | 대학생 | 대학생·취업 준비생·직장인 |
| 분야 | IT·개발 등 일부 분야에 집중 | 이후 학과·직무 확대 |

| 출처 | 수집 가능한 공개 모집 페이지를 선정 | 공고사이트와 개별 단체·기관 홈페이지·공개 SNS |

기존 Q&A·커피챗·크레딧 등 다른 기능은 이번 제품 핵심 범위에서 제외한다. 기존 앱 기능의 삭제 목록이나 코드를 변경하라는 승인으로 해석하지 않는다. 부트캠프 등 개별 유형의 초기 포함 여부는 별도 확정이 필요하다.

## 초기 성공 기준

사용자가 선택한 기준은 “원하는 직무·경험을 선택하면 참여를 검토할 만한 활동을 빠르게 찾는다”다. 시간·품질의 수치 목표는 아직 미정이며, 참여 검토 가능성에 지원 자격을 포함하는 정도를 다음 대화에서 확인한다. 전체 사이트 대체나 기존에 몰랐던 활동 발견을 첫 버전의 필수 완료 기준으로 추가하지 않는다.

## 맞춤 탐색

- 학과에 유관한 직무를 제안한다. 사용자는 학과와 무관한 직무도 직접 선택할 수 있다.
- 사회성·네트워킹 등 얻을 경험을 공통 해시태그로 규격화한다. 개별 태그 사전은 아직 초안이다.
- 경험 태그는 공고 설명과 사용자가 원하는 경험에 따른 추천 양쪽에 사용한다.
- 직무와 경험이 함께 일치하는 활동을 우선 제안한다. 부분 일치 후보에는 직무만 일치하거나 경험만 일치하는 활동도 포함한다. 실제 일치 태그만 강조한다.
- 필터를 선택할 때 결과 개수를 제공한다.
- 전체 조건에 맞는 결과가 없으면 이미 선택한 조건의 부분 조합 중 결과가 있는 조합과 각 활동 수를 제안한다. 결과가 없는 조합은 제안하지 않는다. 새 조건 추가나 유사 태그 교체가 아니다.
- A·B·C 선택은 설명용 예시이며 선택 개수 상한이 아니다. 단일 조건 조합 표시와 조합 정렬·개수는 미정이다. 조건의 AND/OR와 조합 선택 후 즉시 적용·되돌리기는 아래 최신 승인 절을 따른다.

## 자격 안내와 조직·프로그램 스크랩

사용자는 자격을 갖추려고 노력할 수도 있으므로, 부족한 자격을 카드에 보여주고 스크랩할 수 있게 하는 방향을 제안했고 후속 질문에서 저장 대상을 조직·프로그램으로 선택했다. 현재 공고의 자격 안내와 지속 조직·프로그램의 저장을 구분한다. 자격 미충족을 이유로 자동 제외하는 정책은 채택하지 않았다. 다음 모집 자동 알림·자격 달성 추적은 범위에 추가하지 않았다. 사용자 정보는 공고 확인 중 필요한 때 해당 항목을 입력받는 B 방식을 선택했다. 한번 입력한 정보는 다른 공고의 자격 확인에도 재사용하고 언제든 수정할 수 있도록 사용자 승인을 받았다. 구체 항목·저장 위치·보관 정책은 미정이다.

모델 의견은 필수 자격 미충족·정보 부족으로 확인 필요·우대사항을 구분하자는 것이다. 실제 자격 판정 기준과 이번 회차/향후 준비의 표시 방식은 아직 승인되지 않았다.

## 승인된 수집·처리 방향

2026-09-20 사용자가 “좋아 그렇게 해줘”로 직전 수집·ELK 활용 제안을 승인했다.

1. 수집 가능한 공개 홈페이지·모집 페이지를 정해 정기적으로 확인한다.
2. 새로운 단체·모집 페이지를 발견하면 수집 출처를 확장한다.
3. SNS 공고는 연결 가능한 API와 운영자 제보·수동 검토로 보완한다. 모든 공개 SNS 게시물을 자동 수집할 수 있다고 전제하지 않는다.
4. 공고 내용에서 활동 정보와 경험 태그를 정리한다. 활동 근거 기반 추론과 미확정 후보의 관리자 검토는 승인됐으며 구체 추출 방법·운영 구현은 미정이다.
5. 같은 활동의 중복 공고를 통합하고 마감 정보를 갱신하여 활동 수의 신뢰성을 확보한다.

공개 페이지별 수집 가능 여부·접근 조건·실제 추출 품질은 검증 전이다. 수집 주기, 최초 출처 목록, 운영자 제보 방식, 누락·오류 처리 규칙도 미정이다.

기존 구현은 샘플 기반 탐색·저장·상세·지도·일정·개인 일정 겹침이다. 이번 재기획의 자동 수집·맞춤 추천은 구현하지 않았다. 이번 세션에서는 문서와 공식 자료만 확인했으며 수집 실험·빌드·테스트를 실행하지 않았다.

## PostgreSQL 대안 검토 — 미결정

사용자가 ELK에서 PostgreSQL로 대체 가능한 역할을 질문했다. 구조화된 필터·활동 수·부분 조합 집계·규칙 기반 추천은 PostgreSQL과 앱 로직으로 구현할 수 있다. Logstash의 실행 파이프라인과 Kibana의 대시보드 UI는 DB 자체가 제공하지 않아 수집 작업자·관리자 화면 등이 별도로 필요하다. PostgreSQL 우선 검증 후 검색 품질·부하에 따라 Elasticsearch를 추가하는 것은 모델 제안이며, 기존 ELK 활용 승인을 PostgreSQL 채택으로 변경하지 않았다. 성능 시험은 미실행이다.

## 자격 정보 입력 UX 제안 — 승인 전

사용자는 카드의 자격 공간에서 입력을 안내하는 방식을 제안했다. 개선안은 ‘지원 조건’ 영역에 공고의 요구 조건과 확인 상태를 함께 두고, ‘학년 입력’처럼 구체적인 버튼을 제공하는 것이다. 필요한 항목만 하단 시트에서 입력하고 같은 카드로 돌아와 결과를 반영하며, 건너뛰어도 탐색·조직/프로그램 저장은 가능하게 한다. 미입력·명시된 필수 자격 미충족·확인된 항목 충족을 구분한다. 부분 확인을 전체 지원 가능 판정으로 표현하지 않는다. 후속으로 정보의 다른 공고 재사용과 언제든 수정 가능은 승인됐다. 하단 시트 등 상세 UI는 제안 단계이며 저장 위치·보관 정책은 미정이다. 실제 화면 구현·사용자 테스트는 하지 않았다.

## 탐색 단위 재검토

사용자는 모집 마감 공고도 동일한 탐색 흐름에서 보여주기로 했으며, 후속으로 기본 탐색을 프로그램 카드로 하고 개별 모집 공고를 프로그램 상세에서 확인하는 구조를 승인했다. 최근 모집 중인 프로그램이 검색에서 먼저 나오도록 요청했다.

프로그램 하나를 카드 하나로 묶고 상세에서 회차·직군별 공고를 제공한다. 모집 중/종료 상태와 정보의 기준 회차를 명시하고 경험·자격·일정은 공고별 근거를 보존한다. 필터와 부분 조합의 결과 개수는 프로그램 수로 계산하는 것으로 승인됐다. 조건을 충족하는 공고가 여러 개여도 같은 프로그램은 한 번만 센다. 조합별 결과 집합은 겹칠 수 있어 개수를 단순 합산하지 않는다. 서로 다른 회차의 태그·자격을 합쳐 실제 존재하지 않는 전체 일치를 만들지 않도록 검토한다. 모집 중인 프로그램끼리의 정렬은 경험 적합도 → 가까운 모집 마감 → 최근 모집 시작 순으로 사용자 선택(C 다음 B 다음 A)을 받았다. 앞선 기준이 같을 때 다음 기준을 적용하는 순차 정렬로 해석했다. 경험 적합도 계산식·날짜 미확인 처리·종료 프로그램 간 정렬·대표 공고 선정·여러 동시 모집의 요약은 미정이다. 선택 직무 기준으로 모집 상태·우선순위를 판단하는 것으로 승인됐다. 예를 들어 iOS 종료·디자인만 모집 중이면 ‘iOS 모집 종료 · 다른 직무 모집 중’으로 표시하고 iOS 모집 중 프로그램보다 뒤에 노출한다.

## 경험 우선순위와 행동 학습 검토

사용자가 가장 원하는 경험을 지정하도록 결정했다. 좋아요 등 행동으로 추천 가중치를 변경하는 방식은 맹점 검토를 요청받은 단계이며, 스크랩과 추천 반응의 분리는 아래 절에서 후속 승인됐다. 실제 가중치 업데이트 방식은 미정이다.

모델 제안은 명시한 최우선 경험·현재 필터와 행동으로 추정한 선호를 분리하는 것이다. 프로그램 선호를 모든 태그의 선호로 해석하지 않고 자격 준비용 저장을 즉시 지원 의사로 간주하지 않는다. 노출 편향·반복 신호·관심 변화·초기화 등도 검토한다. 필터 개수는 명시 조건으로 계산하고 행동 선호는 순위 보정에 쓰는 안은 승인 전이다. 적합도 미세 점수차로 마감·최신성이 무력화되지 않도록 구간 등 대안을 검토하되 기존 C→B→A를 임의 변경하지 않는다.

## 스크랩과 추천 반응 분리 — 승인

사용자가 “그래요”로 분리안을 승인했다. 스크랩은 조직·프로그램을 다시 보기 위한 목록 저장, 추천 반응은 ‘이런 프로그램 더 추천’이라는 가중치 보정 행동이다. 첫 버전에는 스크랩을 학습 가중치에 반영하지 않고 추천 반응을 학습 신호로 사용한다. 스크랩 해제는 비선호가 아니며 추천 반응은 취소 가능하고 중복 가산하지 않는다. 스크랩은 기본 행동, 추천 반응은 보조 행동이다. 추천 반응의 버튼/더보기 배치와 구체 가중치는 미정이다.

## 태그 유형·프로필 확장 논의

사용자가 경험 태그 6개 초안에 긍정하면서 기획·디자인·백엔드·프론트엔드·창업 등 나아갈 목표 유형과 현재 필요한 경험 유형을 분리하고 싶다고 밝혔다. 프로필에서 지금 필요한 것을 찾도록 유도하는 유형 제안을 요청했다. [방향/경험 2축 문서](tag-types-and-profile-draft.md)의 ‘나아갈 방향’과 ‘지금 필요한 경험’ 구분은 후속 “좋아요”로 승인됐다. 상황형 입력의 세부 문구·선택 수·매핑·창업에 대한 모집 상태 규칙은 확인 전이다.

## 검색 태그 결합 — 최신 승인

방향 태그 여러 개는 기본 하나라도 일치(OR), 방향과 경험 유형 사이는 함께 충족(AND)한다. 특정 방향들을 반드시 함께 원하면 ‘모두 포함’을 선택할 수 있다. 추천은 일부 일치도 후보에 포함한다. 앞선 검색 전체 AND 권고는 이 수정안으로 대체됐다. 2026-09-21 사용자는 경험 태그도 하나라도 일치하면 포함(OR)하되 두 경험 모두 일치하는 프로그램을 먼저 노출하도록 결정했다. 후속으로 모집 상태가 같으면 최우선 경험의 일치를 단순 일치 개수보다 앞세우도록 승인됐다. 최우선 일치 여부가 같은 후보 사이의 행동 점수·일치 개수 관계와 구체 조작 방식은 미정이다. 상세는 태그 유형 문서를 따른다.

## 경험 태그의 근거

2026-09-21 사용자 B 선택으로 구체적인 활동 내용에서 근거 있게 경험 태그를 추론하고 근거를 함께 제공하는 방식을 승인했다. 태그별 적용 기준 초안은 태그 유형 문서에 있다. 사용자는 보류 태그를 나중에 본인이 처리하는 운영 방향과 세부안을 승인했다. 공고와 확정 태그는 노출하고 미확정 후보만 관리자 검토 대기로 둔다. 프로그램/회차·후보 태그·원문·이유를 보고 승인/수정/제외/계속 보류할 수 있으며 미승인 후보는 검색·추천·개수에 반영하지 않는다. 실제 추출 방식·검토 UI는 미정이다.

## 행위별 경험 속성 — 승인

2026-09-22 경험을 행위별 속성으로 구조화하는 보완안을 승인했다. 네트워킹은 누구와, 제작은 무엇을/어떻게로 구체화하며 팀협업은 수행 방식으로 둔다. 모든 행위에 동일 필드를 강제하지 않는다. 속성 조합은 같은 활동의 근거에서 확인하고, 중복 가산과 제작/완성·출시의 혼동을 피한다. 원문에 없는 구체 대상은 추측하지 않는다. 프로필에서 행위를 먼저 선택하고 속성을 선택적으로 추가하며, 선택한 묶음 전체를 최우선 경험으로 지정할 수 있다. 하위 태그 검색 시 행위 경로를 표시하고 복합 조건 하나로 선택한다. 상위 전체 조건을 자동 추가하지 않는다. 같은 모집 상태에서 경험 전체 일치를 부분 일치보다 먼저 추천하며 부분 일치는 맞는 속성만 강조한다. 상세와 미정 항목은 [구조 문서](action-based-experience-tags-draft.md)를 따른다.

## 현재 회차와 과거 경험의 구분 — 승인

2026-09-22 사용자 “네 좋아요”로 승인했다. 현재 추천·필터에는 이번 회차에도 제공된다는 근거가 있는 경험만 반영한다. 지난 회차에서 제공한 경험을 현재 회차에 자동 복제하지 않는다. 과거 경험은 프로그램 상세에 ‘지난 기수에서 제공 · 이번 기수 미확인’으로 구분해 표시한다. 이번 안내에 언급이 없다는 이유로 경험이 없다고 확정하지 않는다.

프로그램 공통 소개가 현재 회차에도 적용된다는 근거의 판단 기준, 여러 회차가 동시에 모집 중일 때의 조합, 현재 모집이 없는 프로그램의 과거 경험 검색 방식은 후속 명세 대상이다. 앱·수집기·추천 구현은 하지 않았다.

## 결과 없는 검색의 조합 선택·되돌리기 — 승인

2026-09-22 사용자 “좋아요”로 승인했다. 결과가 존재하는 부분 조합을 사용자가 선택하면 해당 조합으로 필터를 변경하고 결과를 바로 보여준다. 해제된 조건과 ‘되돌리기’를 표시하며 되돌리면 조합 적용 직전 조건으로 복귀한다. 사용자가 조합을 고르기 전에 필터를 자동으로 변경하지 않는다.

직전 대화의 12개는 가상 예시다. 조합의 결과 수는 기존 계약대로 중복 없는 프로그램 수이며, 이번 승인은 선택·복귀 동작에 관한 것이다. 기존 범주별 AND/OR 규칙을 모든 조건 AND로 바꾸지 않는다. 부분 조합은 실제 적용된 검색 논리에서 결과가 있는 경우만 제안한다. OR 항목 일부 제거는 결과를 늘리지 못할 수 있으므로 단순히 태그 조합을 나열해서는 안 된다. 제안 정렬·노출 개수·단일 조건 조합 포함 여부와 되돌리기 표시 수명은 미정이다.
