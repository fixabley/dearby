# 활동 공고 규격 v1

2026-09-14 기준, 사용자 제공 링크 2건과 CIEAT 메인에서 발견한 공개 상세 공고 3건을 검토했다.
이 자료는 **실제 공고를 수동으로 규격화한 샘플**이다. 자동 크롤러·실시간 모집 현황·개인화 추천의 결과가 아니다.

## 핵심 모델

`Organization(조직)`과 `Activity(개별 공고)`는 별도 식별자를 가진다.
SW마에스트로 13기 공고를 저장하면 SW마에스트로 조직이 남는다는 사용자 정의를 따른다.
제목이나 URL만으로 조직을 합치지 않고 검토한 ID를 사용한다.

### 조직 트리와 여러 공고 (2026-09-14 반영)

조직은 `parentOrganizationId`로 상위 조직을 참조한다. 하나의 조직에는 여러 하위 조직과
여러 공고가 연결될 수 있으며, 공고의 연도·모집 회차가 바뀌어도 조직 ID는 유지한다.
자료 전체에는 여러 최상위 조직이 존재할 수 있다. 상위 조직은 최대 하나이며,
자기 자신·자손을 부모로 지정하는 순환과 존재하지 않는 부모 ID는 검증에서 거부한다.
null은 이 자료에서 확인된 상위 조직이 없다는 뜻이며, 현실에서 독립 조직이라는 보장은 아니다.

사용자가 제시한 탐색 구조:

```text
충북대학교                         조직
└─ 소프트웨어학과                  조직
   └─ 동아리                      분류
      └─ nestnet                  조직 · 즐겨찾기 대상
         ├─ 2026 모집공고          공고
         └─ 2025 모집공고          공고
```

이 예시의 `동아리`는 조직 종류를 묶는 탐색 분류로 해석한다. 따라서 데이터에서는
nestnet의 부모가 소프트웨어학과이며, `kind=community`로 동아리 종류를 구분할 수 있다.
실제 동아리연합회처럼 독립된 운영 주체라면 별도 조직 노드로 등록한다.
예시는 사용자 구상을 설명하며, nestnet의 실제 공고를 수집했다는 뜻은 아니다.

2026·2025 공고에는 각각 다른 `id`를 부여하고 같은 `favoriteOrganizationId`를 연결한다.
기존 `organizationLinks`는 게시자·운영자 등의 공고별 역할이며, 조직의 부모 관계와 별개다.
상위 조직을 저장했다고 모든 하위 조직까지 자동으로 저장하지 않는 것을 현재 기본 동작으로 둔다.
상위 조직 화면에서 하위 조직 공고를 모아보는 정책과 트리 탐색 UI는 후속 설계 대상이다.
이번 변경은 공통 규격·샘플 및 앱 데이터 모델에 계층을 반영한다.

게시자, 운영자, 소개 대상, 문의처는 다를 수 있다. 예를 들어 한국농어촌공사 설명회의
운영부서는 충북대학교 대학일자리센터이고 소개 대상 기업은 한국농어촌공사다.
`organizationLinks.role`로 역할을 구별하고 `favoriteOrganizationId`로 실제 저장 대상을 명시한다.
사용자 승인에 따라 채용 행사는 소개 대상 기업, 대회는 지속되는 대회 프로그램을 저장한다.
활동 분류와 학교 맥락은 조직 소속과 분리한다. [관심 대상 선정 규칙](interest-target-rules.md)을 따른다.
공동 주관 공고처럼 대표 저장 대상을 정하지 못한 경우에는 null로 두고 조직 저장을 활성화하지 않는다.

영남권 대회는 사용자 결정으로 다음과 같이 확정했다.

```text
영남권 AI·정보보호영재교육원
└─ 대회 (탐색 분류)
   └─ 영남권 사이버 공격 방어 대회 (프로그램 조직 · 즐겨찾기 대상)
      └─ 제2회 공고 (edition: 2)
```

교육원과 대회의 부모 관계는 **사용자가 지정한 서비스 내 분류**다.
원문에서 확인한 교육원의 `contact` 역할은 그대로 보존하며 단독 주관으로 바꾸지 않는다.
대회 프로그램 ID는 회차가 바뀌어도 유지하며, 교육원까지 자동 저장하지 않는다.

## 필드 사전

기계 검증 규격: [schema.json](../../shared/contracts/activities/schema.json)

조직 필드: `id`, `name`, `kind`, `sourceIds`, `parentOrganizationId`.
공고 필드는 아래와 같다.

| 필드 | 의미 및 규칙 |
| --- | --- |
| `id` | 사이트 식별자 + 원문 공고 ID. 모집 회차마다 별도 ID |
| `edition` | 원문에 명시된 행사·모집 회차. 미확인·해당 없음은 null |
| `title`, `summary` | 원문에 근거한 제목과 짧은 설명. 홍보 문구나 성과를 사실처럼 추가하지 않음 |
| `kind` | 대회, 진로 행사, 멘토링, 동아리 모집, 학사 행정 등. 원문 게시판 분류와 별개 |
| `sourceIds` | 확인한 본문·포스터·첨부의 출처 ID |
| `organizationLinks` | 게시자·운영자·소개 대상·문의처·주관 등 관계 |
| `favoriteOrganizationId` | 관계를 이어갈 관심 대상 조직·프로그램 ID. 미확정이면 null |
| `targetSelection` | 사용자 승인 또는 편집상 잠정 지정, 적용 규칙 ID와 결정 근거 |
| `categoryPath` | 활동 분류 ID의 경로. 채용은 recruitment → recruitment_event로 정규화 |
| `contexts` | 이번 행사와 관련된 학교 등의 조직 ID, 맥락 역할, 근거 유형. 조직 소속과 분리 |
| `audience` | 누구를 대상으로 하는지: 학력 단계, 학년, 전공, 학교 범위 |
| `eligibility` | 지원에 필요한 필수 조건. 대상 설명과 구별하며 논리 조합을 보존 |
| `interestTags` | 편집자가 붙인 관심사 검색·추천 태그. 지원 자격으로 사용하지 않음 |
| `application` | 접수 기간, 날짜 정밀도, 방법, 필요 서류, 제출 장소 |
| `schedule` | 활동의 단계별 실제 일정. 예선·결선·발표·행사 등을 분리 |
| `location` | 온라인/오프라인/혼합과 활동 장소. 신청서 제출처와 구분 |
| `capacity` | 모집 정원. 미기재면 null. 스냅샷 신청 인원은 실시간 잔여 정원으로 사용하지 않음 |
| `benefits` | 마일리지·기념품·이수 면제 등. 발급 주체와 단위를 보존 |
| `cost` | 참가비. 미기재는 null/unknown이며 무료로 처리하지 않음 |
| `qualityIssues` | 원문 충돌·첨부 미검토·조직 미확정 등과 해결 주체 |
| `demoVisible` | 첫 샘플 피드 표시 여부. 운영 환경의 추천 자격 판정과 별개 |

`status`는 `known`, `partial`, `unknown`, `conflicting`, `not_applicable` 중 하나다.
null은 값을 모른다는 뜻이고, 빈 배열은 수집한 값이 없다는 뜻이다. 둘 다 '제한 없음'을 의미하지 않는다.
`evidence`는 출처 ID와 원문 내 위치를 기록한다. 사진 전체나 개인 담당자 정보는 앱에 복제하지 않는다.
공고 규격의 출처 검토 상태는 **특정 사용자의 지원 가능 판정 결과가 아니다**.

## 조건을 논리로 보존하기

조건 문장 하나를 단순 키워드 여러 개로 흩어놓으면 추천 결과가 달라진다.
대회의 지역 조건은 '질문자 본인이 영남권 거주자여야 함'도, '팀원 모두가 영남권 학생이어야 함'도 아니다.
다음처럼 팀·개인 조건과 AND/OR를 분리한다.

```text
팀 인원 ≤ 4
AND 부문별 학력 조건 충족
AND 팀원 중 최소 한 명:
    학교 소재지가 부산·울산·대구·경남·경북
    OR 거주지가 부산·울산·대구·경남·경북
```

샘플의 `team.division` 값은 **팀원 전원의 해당 부문 학력 충족을 검증한 분류**를 뜻한다.
사용자가 선택한 부문 이름만으로 자격 충족으로 간주하면 안 된다.
원문 일부만 규격화된 경우 `status=partial`로 두며, 추출한 조건 일부를 통과했다고 전체 지원 가능으로 표시하지 않는다.

향후 개인화 판정 결과는 `eligible / ineligible / needs_user_input / needs_source_review`로 구분한다.
- 사용자 학년·소속·팀원 지역 등이 없어 판단할 수 없음: 필요한 항목만 추가 입력 제안.
- 원문 대상 조건 충돌·점수 기준 미확인: 운영자/원문 검토가 필요. 사용자에게 입력을 반복 요구하지 않음.
- 관심 직군 일치: 추천 순위 신호이며 필수 자격을 대체하지 않음.
이번 반복에서는 개인정보 입력이나 자동 자격 판정 엔진을 구현하지 않는다.

## 날짜·장소·혜택 처리

- 시간대는 `Asia/Seoul`. 정확한 시각이 있으면 오프셋 포함 ISO 8601로 저장한다.
- `10월 7일 24:00`은 `2026-10-08T00:00:00+09:00`으로 정규화하고 원문 표현을 함께 보존한다.
- 날짜만 있으면 `opensOn`/`closesOn`에 기록하고, 정확한 시각은 null로 둔다. 23:59를 만들어 넣지 않는다.
- 접수 마감과 행사 종료는 별개다. 예컨대 DB 상담은 접수 16시 마감, 행사 17시 종료다.
- 참여시간 표와 일정에서 계산한 소요 시간이 다르면 이수 시간으로 추측해 병합하지 않는다.
- 온라인 예선과 오프라인 결선은 단계별 장소로 관리한다. 우편 제출 주소를 행사 장소로 사용하지 않는다.
- `CIEAT_POINT`는 씨앗이 발급하는 외부 마일리지다. Dearby 사후 크레딧으로 환산하거나 합산하지 않는다.
- 이미 지난 공고도 샘플 검증 자료로 남는다. 앱은 '검토한 공고 샘플'이라고 명시하며 현재 모집 중으로 단정하지 않는다.

## 수집 경계와 재현

CIEAT 메인 페이지의 프로그램 목록은 동적으로 로드된다. 공개 HTML에 명시된
`POST /clientMain/a/m/getMainProgramApplListAjax.do` (`ablityCategory=ALL`)로 목록을 읽고,
공개 상세 페이지의 `npiKeyId`를 사용해 위 3건을 확인했다. 로그인·신청·찜하기는 실행하지 않았다.

원문 검토 기준은 `sample.json`의 `snapshotAt`과 출처별 `checkedAt`이다.
본문/포스터가 변경될 수 있으므로 실제 추천 데이터로 전환하기 전에 원문과 첨부를 재검증해야 한다.
이 작업에는 주기 수집, 재배포 권한 검토, 중복 공고 병합, 개인정보 저장 기능이 포함되지 않는다.

샘플 파일 수정 후:

```sh
npm ci
python3 scripts/sync-activity-samples.py
npm test
```

샘플의 기준 파일은 `shared/contracts/activities/sample.json` 하나다.
iOS·Android의 JSON 리소스는 위 스크립트로 복사하며 `--check`로 일치 여부를 확인한다.
