# 네이티브 앱 구조 원칙

GitHub #1의 사용자 승인 Seed v2를 구현 기준으로 삼는다. 기존 화면·문구·제스처·즐겨찾기 저장 형식과 동작을 유지하며 실제 UI 정비는 #2에서 진행한다. iOS 26+ SwiftUI와 Android API 31+ Compose의 기능 구분과 책임을 맞추되 플랫폼별 상태 관리는 각 프레임워크에 맞춘다.

## 기능과 책임

| 구분 | 책임 | 포함하지 않는 책임 |
| --- | --- | --- |
| App / app | 앱 진입, 실제 의존성 생성, 탭·화면 조합, 공유 상태 소유 | 카드·목록의 상세 렌더링, 저장 구현 |
| Features / feature | Discovery, Favorites, NoticeDetail의 화면·기능별 UI | 디스크·번들 직접 접근 |
| Shared / core의 model | 공고·조직 모델, 조회와 표시를 위한 순수 계산 | 플랫폼 저장소·뷰 의존성 |
| Shared / core의 state | 즐겨찾기 ID의 단일 상태와 저장·삭제 이벤트 | View 생성, 구체 저장 구현 |
| Shared / core의 data | 카탈로그 공급·즐겨찾기 저장 경계와 실제 로컬 구현 | 사용자 화면 구성 |
| Shared / core의 UI | 실제로 여러 기능에서 쓰는 표시 컴포넌트 | 저장소 접근, 공유 상태 생성 |

위 표는 책임의 대응이다. Swift 파일과 Kotlin 패키지의 대소문자·타입명은 관례에 맞춘다. 한 번 쓰는 컴포넌트는 해당 기능에 두고 실제 재사용될 때 옮긴다. 파일 길이 제한을 맞추기 위한 분리나 기능 없는 계층을 추가하지 않는다.

## 디렉터리 배치 예시

다음은 책임을 찾기 위한 예시이며 실제 파일 트리와 이름은 각 앱의 ARCHITECTURE.md에 기록한다.

```text
App/                         # Android: app/
  앱 진입·조립·루트 화면
Features/                    # Android: feature/
  Discovery/                 # discovery/
    탐색 화면·공고 카드
  Favorites/                 # favorites/
    즐겨찾기 화면·조직 행
  NoticeDetail/              # noticedetail/
    공고 상세 화면
Shared/                      # Android: core/
  Models/                    # model/
    공고·조직·카탈로그 모델
  State/                     # state/
    즐겨찾기 상태와 이벤트
  Data/                      # data/
    카탈로그 공급·즐겨찾기 저장 인터페이스와 로컬 구현
  UI/                        # ui/
    공통 정보 표시
```

새 공고 카드 표현은 Discovery에, 즐겨찾기 행은 Favorites에 둔다. 여러 화면에서 필요한 상태는 루트에서 한 번 생성해 주입한다. 향후 서버 카탈로그를 추가할 때는 Data의 공급 경계 구현과 App의 조립을 변경하며 카드 View의 저장·네트워크 코드를 추가하지 않는다. API 구현은 이번 범위에 없다.

## 데이터와 이벤트 흐름

```text
앱 조립 → 카탈로그 공급 경계 → 번들 로컬 구현
앱 조립 → 즐겨찾기 상태 → 즐겨찾기 저장 경계 → 로컬 저장 구현
앱 조립 → 화면(표시 데이터·이벤트 콜백) → 재사용 UI
UI 이벤트 → 즐겨찾기 상태 변경 → 관련 화면의 관찰·재구성
```

재사용 UI는 표시 데이터와 이벤트 콜백으로 동작한다. UserDefaults, SharedPreferences, 번들 파일, 네트워크에 직접 접근하지 않는다. 표시 모델의 조회·계산은 순수해야 하며 모델 생성이 저장소 접근을 유발해서는 안 된다.

카탈로그 공급은 현재 번들 샘플을 유지하되 테스트용 공급자로 바꿔 끼울 수 있는 최소 경계를 둔다. 미래 네트워크의 인증·페이지네이션·재시도 정책을 미리 구현하지 않는다.

즐겨찾기는 앱에서 하나의 상태 인스턴스를 소유하고 읽기 상태와 저장·삭제 동작을 주입한다. 저장은 토글이 아닌 멱등 추가이며 해제는 명시적 삭제다. 조직 ID, 저장 키와 기존 데이터 호환성, 상위 조직 자동 저장 금지, 학교 맥락과 관심 대상 구분을 보존한다.

## 플랫폼별 상태 관리

iOS는 Observation과 SwiftUI 상태 소유 규칙을 사용한다. 공유 상태는 안정된 루트 수명에 두고 UI와 관련된 변경은 MainActor에서 관리한다. sheet 선택, 카드 위치·피드백 같은 임시 UI 상태는 가장 가까운 화면에 둔다.

Android는 Compose의 상태 관찰과 단방향 이벤트 전달을 사용한다. 상태 소유자의 재생성과 Activity 재생성 시 저장 복원을 명시하며 재사용 Composable이 저장소를 생성하지 않는다. 탭과 pager 등 UI 상태의 기존 생명주기를 유지한다.

새 외부 상태 관리·DI 라이브러리와 별도 빌드 모듈을 도입하지 않는다. 테스트용 의존성은 생성자나 함수 인수로 주입한다. 구체 구현을 바꿔야 하는 경계만 interface/protocol로 만든다.

## 완료 검증

- 두 앱의 실제 디렉터리 트리, 상태 소유와 의존 방향, 새 기능 배치 예시를 각 앱 문서에 남긴다.
- 임시 저장소를 주입해 앱 실행 없이 저장·중복 저장·삭제와 공유 상태의 일관성을 검증한다. 기존 영속 저장 구현의 재생성 후 복원도 확인한다.
- 기존 카드 넘기기, 더블탭/버튼 저장, 즐겨찾기 목록, 연결 공고 상세, 삭제, 재실행 후 저장 유지와 기존 저장 데이터 호환성을 회귀 검증한다.
- 두 앱 빌드와 관련 테스트 결과를 기록한다. 실행하지 않은 UI·기기 검증은 통과로 표시하지 않는다.

앱 PR들은 서로의 코드 변경에 의존하지 않으며 각각 main 대상으로 검토한다. 권장 검토 순서는 공통 원칙 → 두 앱이다. 한 플랫폼 PR만으로 #1을 닫지 않는다. API와 #2 UI 전환은 포함하지 않는다.
