# API 게스트 홈 화면 세션 잇기 인계

2026-10-06 KST. 계약: #95(6e82e10) native-v1 「홈 화면 세션 잇기」. 마이그레이션 PR #109 → API PR(이 문서) 순서이며 둘 다 #84 위에 쌓았다. 로컬 구현·테스트 결과이며 운영 DB·ingress·배포는 바꾸지 않았다.

## 구현

- `POST /v1/guest/handoffs`: 게스트 프록시와 기존 토큰이 필요하다. 201 `{code, expiresAt}`. 코드는 32바이트 무작위 base64url(43자), 수명은 10분이다. 세션당 행은 1개(UNIQUE)이므로, 새로 발급하면 이전 코드의 digest가 바뀌어 이전 코드는 즉시 404가 된다.
- `POST /v1/guest/handoffs/redeem`: 게스트 프록시가 필요하고 토큰은 받지 않는다. body `{code}`, 200 `{guestToken}`. 없음·만료·사용됨·교체됨·세션 폐기는 모두 같은 404 본문이다. body 형식 오류만 422다. 성공하면 같은 트랜잭션에서 `used_at`을 기록하고 암호문을 지운다.
- 저장: 코드 SHA-256 digest, 세션, `expires_at`, `used_at`, 그리고 토큰 암호문이다. 키는 `HKDF-SHA256(code, salt "dearby/guest-handoff", info "v1 token key")`, 암호는 AES-256-GCM(무작위 12바이트 IV)이고, 세션 digest를 AAD로 써서 암호문을 자기 행에 묶는다. DB만으로는 코드 원문이 없어 복호화할 수 없다.
- 만료 암호문은 다음 핸드오프 요청(발급·교환 모두)에서 전체를 대상으로 지운다. 요청이 없으면 남지만, 코드 없이는 복호화할 수 없다.
- 요청 제한은 기존 guest 카운터다. 교환은 토큰이 없으므로 전역 1,200/분에만 걸리며 실패도 센다. 발급은 세션당 120/분에도 걸린다.

## 서버 비밀값을 키 파생에 섞지 않은 이유

코드 자체가 256비트 무작위 bearer 값이고 DB에는 그 digest만 있다. 따라서 DB가 유출되어도 코드 없이 토큰을 복원할 수 없다. 코드를 가진 사람은 서버 비밀값과 관계없이 redeem API로 토큰을 받을 수 있으므로, 비밀값을 섞어도 막는 공격이 늘지 않는다. 반대로 `GUEST_PROXY_SECRET`에 결합하면 비밀값 교체 시 발급된 코드가 깨지고, 두 용도(프록시 인증·암호화)가 한 값에 묶인다. 그래서 섞지 않았다.
