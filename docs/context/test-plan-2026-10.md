# 비공개 테스트 계획 — 2026-10-26

2026-10-26 사용자 결정: 비공개 테스트의 성공 기준을 둘로 정한다. ① 내 활동에 추가한 활동이 실제 참석까지 이어지는가, ② 테스터 1인이 명함 교환을 3회 이상 하는가. 측정 이벤트는 [analytics-v1.md](../../shared/contracts/analytics-v1.md) "비공개 테스트 성공 지표"에 정의했고, 앱 구현은 다음 작업이다(아래 "구현 전 상태"). 목표값은 모두 **추정**이며 첫 측정 뒤 고친다.

## 목적

- Dearby의 두 핵심 가치가 실제 사용으로 이어지는지 확인한다: 발견한 활동을 끝까지(참석) 가져가는 도구인지, 현장에서 명함 교환이 실제로 일어나는지.
- 지표가 낮으면 어디서 끊기는지(추가는 했지만 통과 표시를 안 함 / 명함을 받았지만 건네지 않음 등) 깔때기로 보고 다음 개선 대상을 고른다.

## 지표 정의와 계산

### 지표 1 — 활동을 추가하고 실제 참석까지 이어지는가

- **정의**: 내 활동에 추가한 활동 중, 선발 과정을 지나 활동 일정(`Schedule.phase = ACTIVITY`)에 도달하고 참석으로 이어진 비율.
- **참석 판정** 두 가지(둘 다 기록한다):
  - 당일 행동(앱 이벤트): 활동 일정 블록이 진행 중인 날에 그 활동에서 시간표 열기·세션 찜·진행 단계 열기·활동 상세 열기 중 하나를 함 → `activity_day_action`.
  - 수동 판정(서버 기록): 활동 일정 시작 시각이 지났고 선발 단계에 `FAILED` 표시가 없음. 앱 이벤트가 아니라 서버 테이블로 센다(아래 "서버 기록으로 대조").
- **계산식(GA4)**: 활동별로
  - 도달율 = `participation_reached` 사용자 수 ÷ `myactivity_add` 사용자 수
  - 참석율 = `activity_day_action` 사용자 수 ÷ `myactivity_add` 사용자 수
- **GA4 탐색**: 유입경로 탐색, 단계 `myactivity_add` → `participation_reached` → `activity_day_action`, 세그먼트 또는 필터 `signed_in = yes`, 분류 측정기준 `activity_id`(폐쇄형 깔때기, 기간은 테스트 전체). 활동별 수치가 아니라 전체 비율이 필요하면 자유 형식 탐색에서 측정기준 `activity_id`, 측정항목 총 사용자, 이벤트 이름 필터로 세 열을 만들어 나눈다.
- **우아콘 2026의 실제 단계(운영 API `GET /v1/activities/156`, 2026-10-26 확인)**: 선발 과정 = `신청 기간`(모집 슬롯, 2026-10-08 마감)·`입장권 추첨 결과 발송`(ANNOUNCEMENT, 날짜 없음), 활동 일정 = 활동 기간 10/28 + `오프닝 키노트`·`오전 세션`(시간표 있음)·`쉬는시간`·`오후 세션`(시간표 있음). 컨퍼런스지만 선발 단계가 둘이라 `participation_reached`는 테스터가 두 단계를 `통과`로 표시해야 나간다(`via=selection_passed`). 신청 마감이 이미 지났으므로 10/27에 추가하는 테스터는 지난 단계를 **직접 통과로 표시**해야 한다 — 테스터 부탁 1에 넣었다. 따라서 우아콘 깔때기도 추가 → `stage_mark(kind=passed)` → `participation_reached` → `activity_day_action` 네 단계 그대로다.
- 모집 슬롯도 `SELECTION` 세부 일정도 없는 활동만 추가하는 순간 `participation_reached(via=no_selection)`가 함께 나가 도달율이 늘 100%이고, 그런 활동은 "추가 → 당일 행동"(참석율)만 본다. 운영 데이터에 그런 활동이 있는지는 측정 때 `via` 분포로 확인한다.

### 지표 2 — 명함 교환 3회

- **정의**: 테스터 1인이 **맞교환**(내가 받은 명함의 주인이 내 명함도 가진 상태, `Receipt.reciprocal = true`)을 3건 이상 완료한다. 단방향 저장(상대가 브라우저에만 저장, 또는 내 명함을 건네지 않음)은 세지 않는다.
- **계산식(GA4)**:
  - 달성률 = `card_exchange_milestone` 사용자 수 ÷ 기간 안 활성 사용자 수(`signed_in = yes`)
  - 분포 = 자유 형식 탐색, 측정기준 사용자 속성 `card_exchanges`, 측정항목 활성 사용자(0·1·2·3+ 로 몇 명인지)
  - 깔때기 = `screen_view(screen_name=card_qr)` → 웹 `card_view`·`card_open_app`(웹 스트림) → `card_received` → `card_exchange_completed` → `card_exchange_milestone`. 웹 쪽은 비로그인·다른 기기라 사용자 단위로 이어지지 않으므로 건수 비교만 한다.
- **구조적 한계**: 맞교환은 **양쪽 다 Dearby 계정과 명함이 있어야** 성립한다. 비로그인 저장자는 명함이 없어 영원히 단방향이다. 그래서 "3회"는 테스터끼리, 또는 앱을 깐 지인끼리 교환해야 가능하다. 테스터 모집·현장 배치(우아콘에 같은 시간대에 4명 이상)가 이 지표의 전제다.
- **세는 단위**: `card_exchanges`는 맞교환 Receipt 수라 한 사람이 명함 두 장을 건네면 2로 센다. 정확한 "상대 계정 수"는 서버 `receipts`로 대조한다.

### 측정 단위와 한계(공통)

- GA 사용자 수는 Analytics 앱 인스턴스(기기) 단위다. 사용자 ID를 보내지 않기로 한 결정(analytics-v1.md 개인정보 원칙)을 유지하므로 한 테스터가 iPhone·Android 둘을 쓰면 둘로 보인다. 테스터 수가 적어(10~20명) 한 명이 5~10%p를 움직이니 비율과 함께 **명수**를 적는다.
- GA4 탐색 데이터는 24~48시간 뒤 채워진다. 당일 확인은 Firebase DebugView·GA 실시간으로만 한다.
- 맞춤 측정기준(`activity_id`, `via`, `action`, `reciprocal`, 사용자 속성 `card_exchanges`)은 등록 전 데이터에 쓸 수 없다. **10/27까지** GA 콘솔에 등록한다(analytics-v1.md "GA 콘솔에서 할 일").

## 테스터에게 부탁할 행동 3개

1. **활동 추가와 결과 표시**: 우아콘 2026(그리고 관심 있는 활동 1개 이상)을 `내 활동`에 추가한다. 우아콘은 진행 단계의 `선발 과정`에서 `신청 기간`·`입장권 추첨 결과 발송`을 결과대로 `통과`(입장권을 받았으면) 또는 `탈락`으로 표시한다 — 신청 마감(10/08)이 지나 기본값은 `대기`로 남으므로 직접 표시해야 `참여 중`이 된다. 다른 활동도 결과가 나올 때마다 같은 식으로 표시한다(표시는 본인 기록이며 주최 측 결과가 아님을 안내).
2. **당일 앱 열기**: 활동 당일 앱에서 그 활동의 시간표를 열고 들을 세션을 찜한다(우아콘은 오전·오후 블록 각각).
3. **명함 교환 3명 이상**: 미리 명함 1장을 만들어 두고, 현장에서 테스터끼리 `QR 보이기`로 명함을 주고받는다. 받은 쪽은 반드시 `내 명함도 건네기`까지 눌러 `맞교환` 배지를 확인한다. 상대가 앱이 없으면 단방향으로 남아 지표에 들지 않는다는 점을 알려 둔다.

## 측정 전 전제

- **동의 뒤에만 수집**: 테스터 안내문에 사용 통계(Firebase Analytics, 광고 ID·사용자 ID·이름·연락처 없음) 수집을 명시하고 참가 동의를 받는다. 앱 안에서는 개인정보 동의 화면을 지난 로그인 사용자만 내 활동·명함을 쓸 수 있으므로 지표 이벤트는 모두 그 뒤에만 나간다. 현재 `설정 › 개인정보 › 사용 통계 보내기`는 **기본 켬**(opt-out)이다 — 끈 테스터는 지표에서 빠지며, 별도 opt-in으로 바꾸는 것은 앱 변경이라 이 계획의 범위 밖이다(사용자 판단).
- **비로그인 제외**: 모든 비율은 `signed_in = yes`로 거른다. 웹(비로그인)은 교환 깔때기의 상대편 건수(`card_view`·`card_open_app`·`card_save_browser`)로만 본다.
- 운영 서버·운영 GA 속성(앱 스트림)으로 측정한다. 실기기 Debug 빌드도 운영 origin을 가리켜야 한다([현재 작업과 결정](coordinator-current-task-and-decisions.md) 2026-10-25 기록).
- 이벤트는 활동 id·세션 id·개수만 담고 명함 id·명함 내용·상대 계정을 담지 않는다(analytics-v1.md 개인정보 원칙 그대로).

## 서버 기록으로 대조

GA는 기기 단위·동의한 사람만이라 참값이 아니다. 테스트 종료 때 운영 DB(읽기 전용)로 같은 수치를 한 번 대조한다: 지표 1 수동 판정은 `user_activities` × `schedules(phase = ACTIVITY, 시작 시각 경과)` × `user_activity_schedule_statuses(FAILED 없음)`, 지표 2는 `receipts`에서 회수·철회되지 않은 맞교환 쌍(계정 쌍 기준)을 사용자별로 센다. 세션 찜은 `user_session_favorites`. 결과는 명수만 기록하고 개인 식별 정보는 문서에 적지 않는다.

## 구현 전 상태(2026-10-26)

계약에 정의한 `stage_mark`, `participation_reached`, `activity_day_action`, `favorite_add(type=session)`, `card_received`, `card_exchange_completed`, `card_exchange_milestone`, 사용자 속성 `card_exchanges`, 화면 `card_qr`는 아직 iOS·Android에 없다. 10/27 빌드는 앱 작업이 바로 배정될 때만 가능하다. 들어가지 않으면 우아콘 당일 지표 1-가는 `screen_view(timetable)`·`activity_view(source=my_activity)`의 날짜와 서버 `user_activity_schedule_statuses`로, 지표 2는 서버 `receipts`로만 대신 본다.
