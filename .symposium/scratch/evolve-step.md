# Evolve-step — Cycle 1 (완료)

사용자 요청: #1 이슈의 Seed를 더 다듬어서 반영한다. 앞선 구현 진행 요청은 유지하되 Seed 정교화가 선행한다. 구현 배정은 아직 하지 않았다.

## Seed v1

```yaml
goal: iOS·Android의 컴포넌트·디렉터리·상태 관리 원칙을 문서화하고 현재 화면과 동작을 유지하면서 기존 코드를 리팩터링한다.
constraints:
  - iOS와 Android에 적용하며 API는 제외한다.
  - 기능 구분과 책임은 맞추고 상태 관리는 SwiftUI·Compose에 맞게 설계한다.
  - 화면·재사용 UI·상태·데이터 저장의 책임을 분리한다.
  - 플랫폼 기본 컴포넌트를 우선하며 실제 외형 변경은 후속 네이티브 UI 이슈에서 진행한다.
acceptance_criteria:
  - 기능·책임별 디렉터리와 컴포넌트 분리가 두 앱에 적용된다.
  - 상태 소유·변경, 데이터 저장, 의존 방향과 새 기능 추가 기준이 문서화된다.
  - 카드 넘기기·더블탭 저장·즐겨찾기 목록·상세·삭제·재실행 후 저장 유지가 보존된다.
  - 두 앱의 빌드와 관련 테스트를 통과하고 회귀 검증 결과를 기록한다.
```

## Blind Spot Candidates

### Q1. Missing user perspectives

- A — accepted: 새 개발자가 기능 위치를 찾기 쉽도록 기능별 디렉터리 트리와 파일 배치 예시를 완료 기준에 포함한다.
- B — accepted: UI를 고치는 개발자가 데이터 저장을 알 필요 없도록 재사용 UI는 표시 데이터와 이벤트 콜백으로 동작하고 저장소에 직접 접근하지 않는 제약을 둔다.
- C — accepted: 검증 담당자가 앱 실행 없이 핵심 동작을 확인하도록 즐겨찾기 상태 로직을 임시 저장소로 독립 테스트할 수 있음을 완료 기준에 포함한다.

### Q2. Cut-off possibilities

- D — accepted: 향후 API 연결을 위해 현재 번들 데이터 공급을 교체할 경계를 두되 실제 네트워크 구현은 제외하는 제약을 둔다.
- E — accepted: 여러 화면에서 같은 조직을 저장·삭제할 때 일관되게 갱신되도록 즐겨찾기 상태의 단일 소유와 변경 전달 경로를 제약에 명시한다.
- F — accepted: 작은 현재 앱에 과한 구조를 도입하지 않도록 새 외부 상태 관리·DI 라이브러리와 별도 빌드 모듈 분할 없이 기존 도구로 리팩터링하는 제약을 둔다.

최초 제안 시에는 어느 후보도 자동 채택하지 않았다. 아래 사용자 응답에 따라 여섯 후보를 모두 채택했다.

Q1 사용자 응답: “다 채택한다” — A·B·C 모두 승인. Q2의 D·E·F는 아직 선택 대기이며 자동 채택하지 않는다. 전체 Seed v2와 GitHub 본문 갱신은 Q2 답변 후 수행한다.

Q2 사용자 응답: “다 채택한다” — D·E·F 모두 승인. A~F 전부 accepted이며 선택 대기는 종료했다.

## Transferred Meaning

- goal: 변경 없음. 기존 화면·동작을 유지하는 양 플랫폼 구조 리팩터링이다.
- A → acceptance_criteria: 기능별 디렉터리 트리·파일 배치 예시를 명시했다.
- B → constraints: 재사용 UI의 입력·이벤트 경계와 저장소 직접 접근 금지를 명시했다.
- C → acceptance_criteria: 앱을 띄우지 않는 임시 저장소 기반 즐겨찾기 상태 테스트를 명시했다.
- D → constraints: 교체 가능한 데이터 공급 경계와 실제 네트워크 연결 제외를 명시했다.
- E → constraints: 즐겨찾기 상태의 단일 소유와 화면 간 일관된 변경 전달을 명시했다.
- F → constraints: 새 외부 상태 관리·DI 라이브러리 및 별도 빌드 모듈 분할을 제외했다.

각 후보는 위에 표시한 Seed 슬롯 하나에만 반영했다. 기존 제약과 완료 기준은 유지했다. Q1 직후의 대기 문장은 당시의 이력이며 현재는 모두 승인 상태다.
